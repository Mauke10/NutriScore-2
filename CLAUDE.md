This file is a handoff for whichever Claude session works on this repo next. ## Repo layout

The GitHub repo is `Mauke10/NutriScore-2`. The Next.js app lives in the **`nutriscore-app/`** subfolder, not at the repo root, so run all `npm` commands from there (`cd nutriscore-app && npm install && npm run build`). All paths in this file (`app/...`, `lib/...`, `supabase/...`) are relative to `nutriscore-app/`.

## What this app is

A private nutrition + training tracker for two people, Martin and Laura, built around their shared goal of the **Ironman 70.3 Tallinn in August 2027**. It is not a general-purpose product — there are exactly two users, hardcoded as `martin` and `laura` throughout the codebase, no signup flow, no multi-tenancy. Treat "add a feature for a third person" or "make this generic" as out of scope unless explicitly asked.

Both people log into the same app and see each other's data (it's a shared household tool, with a "Compete" tab that turns tracking into head-to-head comparisons). Login is PIN-based, not email/password.

## Stack

- **Next.js 14.2.35, App Router.** Route Handlers under `app/api/*/route.js`, Server + Client Components under `app/`.
- **Supabase (Postgres)** as the only datastore, accessed exclusively through the service-role key server-side (`lib/supabase.js`). No RLS policies are defined for the anon key — RLS is enabled on every table as a safety net, but **all access goes through Next.js API routes**, never direct client-to-Supabase calls.
- **Plain CSS**, no Tailwind, no CSS-in-JS. Everything lives in `app/globals.css`, which has grown into the project's whole design system (CSS custom properties for theming, motion tokens, component classes). Read it before adding UI — there is very likely already a class/token for what you need.
- **lucide-react** for icons.
- No test suite, no CI config, no ORM/migration tool — see "Database" below for how schema changes actually get applied. Verification is the **`nutriscore-verify` project skill** (`.claude/skills/nutriscore-verify/`): a clean build served locally, scripted headless-Chromium runs against mocked `/api/*` with a test login (phone + desktop, light + night), a hydration check, and an in-memory Postgres (PGlite) check that a migration is re-runnable and matches `schema.sql`. Use it after every change.

## Auth

Two-tier PIN system, both paths live in `app/api/login/route.js`:

1. **Per-person PIN (current, preferred path).** `people.pin_hash` holds a scrypt hash (`lib/pin.js`: `hashPin`/`verifyPin`, random 16-byte salt, `salt:hash` hex format, timing-safe compare). Set via Settings → "Change your PIN" (`app/api/change-pin/route.js`), scoped so a person can only ever change their own hash.
2. **Shared legacy PIN (fallback).** The original mechanism — one `APP_PIN` env var, checked with `checkPin()` in `lib/session.js`. Login falls back to this when: (a) the person hasn't set their own PIN yet (`pin_hash` is null), or (b) **Supabase is unreachable** — the `pin_hash` lookup is wrapped in try/catch specifically so a Supabase outage/pause never blocks login entirely.

Session: a signed cookie (`nutriscore_session`), HMAC-SHA256 over `personId.issuedAtMs`, 90-day expiry, timing-safe verification. `currentPerson()` in `lib/auth.js` reads it server-side.

**Explicit product decision — do not add without being asked again:** no PIN brute-force/lockout protection. The user considered this and declined it ("The pin thing is no problem right now as it is only to ppl"). Don't add rate-limiting or lockout to the login route as a "security improvement" unasked.

## Database

`supabase/schema.sql` is the full current schema (fresh-install source of truth). Numbered migration files (`migration_002` through `migration_013`) are additive deltas applied by hand — **there is no migration runner**. Each one is written to be safe to re-run (`if not exists` everywhere). When you need a schema change: write a new `migration_00N_description.sql`, and also update `schema.sql` so a fresh install matches. The user runs these manually in the Supabase SQL Editor — there's no automated pipeline, so after writing a migration, tell them explicitly that they need to go run it.

Tables, in brief:
- `people` — exactly two rows (`martin`, `laura`), `pin_hash` nullable (see Auth).
- `weekly_logs` — one row per person per week, unique on `(person_id, week_start)`. The app's edit feature for this table works by resubmitting the same `week_start`, which upserts in place — no PATCH endpoint exists or is needed.
- `bloodwork` — same shape, unique on `(person_id, panel_date)`, same upsert-based edit pattern.
- `food_logs` — meals/snacks, `meal_type` is `'meal' | 'snack'`. Has a real `PATCH /api/snacks` endpoint (partial update by `id`, scoped to the caller's own `person_id`) because there's no natural per-day unique key here — several entries per day are normal.
- `training_sessions` — manually-logged workouts (swim/bike/run/strength/mobility/other, plus an optional `feel` 1–4 from migration 013 and an `effort` key from migration 014 — `z1`…`z5` for run/bike, `rpe1`…`rpe5` for swim, `light|moderate|hard|max` for the rest; scales live in `effortsFor()` in `lib/trainingSports.js`, the API drops a key that doesn't fit the sport, never rename a key), also has a real `PATCH /api/training-sessions` for the same reason (multiple sessions per day are normal, no upsert key).
- `recipes` + `recipe_ingredients` — saved meals, shared across both people (not owned by one person). `recipe_ingredients` holds per-100g macros so changing portion size recomputes totals; `food_id` links an ingredient to the `foods` row it was picked from, but the macros are still copied onto the ingredient so editing a food never changes old recipes.
- `foods` — the food database behind ingredient search (migration 009). ~4,050 rows from **Fineli** (Finnish food composition database, THL, CC BY 4.0 — the credit line in `FoodSearch.js` is a licence requirement, keep it) plus `source = 'custom'` foods added from the app. Seeded by `supabase/seed_009_fineli_foods.sql`, which is **generated** by `scripts/fineli/build-seed.mjs` from the Fineli CSV package + `scripts/fineli/et-names.json` (Estonian display names and search synonyms keyed by Fineli ID) — edit the JSON and re-run the script, never the SQL. The seed upserts on `(source, source_id)` and never touches `use_count`. `search_text` is lowercased + accent-stripped by `lib/foodText.js` (shared by the seed script and `/api/foods`, so they can't drift); search is per-word `ilike` on a pg_trgm index, ranked by `rankFoods()` (most-used first, via the `bump_food_use()` SQL function called after logging/saving with ingredients).
- `settings` — one row per person, `calorie_target`/`protein_target`/`swim_goal_km`/`bike_goal_km`/`run_goal_km`/`accent_color`/`measurement_parts` (text[], which body parts the Measurements card shows, in order), plus the drawer's Settings (migration 011, read/written via `/api/prefs`): `race_name`/`race_date` (countdown), `day_end_hour` 0–4, `share_meals`, `show_fiber`, `strava_autosync`.
- `body_measurements` — one row per person per day per body part (`part` is a key from `app/dashboard/measurementParts.js`, or `custom:<name>`; never rename a key). Unique on `(person_id, measured_on, part)`, so re-logging a day upserts. `/api/measurements` GET also folds `weekly_logs.waist_cm` into the waist series (dated to the week's Monday) so waist isn't typed twice.
- `training_volume` — monthly, Strava-synced (`source: 'strava'`), separate from `training_sessions` on purpose so a re-sync can never clobber or double-count a manually-logged session. Also holds `weight_moved_kg` (typed in on the Training tab's Month view, under Strength). The Compete tab still reads the monthly totals.
- `strava_activities` — one row per Strava activity (migration 013), keyed on Strava's own activity id. `POST /api/strava/sync` pulls this month + last month (the last 4 months the first time a person has no rows), upserts each activity, deletes rows in that range that are gone on Strava, and rewrites each month's `training_volume` swim/bike/run totals (never `weight_moved_kg`). `activity_date` is the local start date (`start_date_local`), so months and days are counted in local time. `sport` is mapped by `stravaSport()` in `lib/strava.js`.
- `training_plan_items` — planned sessions on the Calendar tab, any number per person per day (migration 012): `activity` text + a manual `done` tick. The sport isn't stored; `lib/trainingSports.js` reads it from the text (`sportOf`, English + Estonian words, brick/rest win) and pulls planned km per sport out of it (`distancesOf`, splits on `+`/`,`/`ja`, skips times and intervals). A plan also shows as done when a workout of the same sport exists that day — a `training_sessions` row or a `strava_activities` row (`GET /api/training-plan` returns both as `sessions`). `POST /api/training-plan` with `alsoPartner` is the one place you write to the other person's plan ("Plan it for Laura too").
- `strava_accounts`, `daily_notes`, `training_plan` — OAuth tokens, a daily shared whiteboard note, and the old one-line-per-day plan (superseded by `training_plan_items`, nothing reads it, safe to drop once 012 is applied), respectively.

## Date handling — the single most important gotcha in this codebase

**Never compute "today" with `new Date().toISOString().slice(0, 10)`.** Tallinn is UTC+2/+3, so for roughly 2-3 hours after local midnight, that expression still returns *yesterday's* date. This has caused two real bugs already (both fixed): the 7-day calorie trend silently excluding anything logged right after midnight, and the Compete tab's "today's calories" going blank for the same window.

Always use the helpers in `app/dashboard/utils.js`:
- `todayStr()` — today's date as `YYYY-MM-DD`, local time, **shifted by the person's "Day ends at" setting** (`setDayEndHour()`, 0–4 h, cached in localStorage `nutriscore-day-end-hour`): at 01:30 with day end 03:00 it still returns yesterday, so late snacks land on the evening. `dateDaysAgo()`, `shortDateLabel()` and `proteinStreak()` use the same shifted "now" (`foodNow()`); week maths (`mondayOf`) and the training calendar use the real clock.
- `localDateStr(d)` — same, for an arbitrary `Date`.
- `mondayOf(d)` — the Monday of that date's week, local time.

If you ever see `toISOString()` used to derive a calendar date anywhere in this codebase, that's almost certainly a bug — grep for it (`grep -rn "toISOString" app/`) as a sanity check after any date-related change.

## Auto-update mechanism (don't "fix" this without understanding why it's shaped this way)

`app/VersionWatcher.js` polls `/api/version` and compares it against `NEXT_PUBLIC_BUILD_TIME` baked into the currently-loaded bundle. If they differ, it reloads the page once — this is what makes a home-screen PWA pick up a new deploy without the user manually closing and reopening it.

It previously caused an infinite reload loop (the bug that opened the last session): every reload re-ran the check, found the same mismatch again, and reloaded again, forever, blocking login. The fix was a `sessionStorage` guard (`nutriscore-reloaded-for-build`) that remembers "I already reloaded for this exact build" so it only ever reloads once per real deploy, with a try/catch fallback for storage-blocked contexts (private browsing). If you touch this file, preserve that guard — removing it reintroduces the reload loop.

## Offline handling

`public/sw.js` is intentionally narrow: it only caches the static app shell (JS/CSS bundle, `public/offline.html`) and only for same-origin GET requests. It explicitly never touches `/api/*` or any non-GET request — this app's data lives in Supabase, so caching an API response would mean showing stale numbers as if current, or letting a save silently "succeed" from cache. Network-first for everything, so a fresh deploy always wins over a cached one (keeps it compatible with VersionWatcher above). `app/OfflineBanner.js` shows a plain-language banner the moment `navigator.onLine` goes false. `app/ServiceWorkerRegister.js` only registers the worker in production (`NODE_ENV !== "production"` bails early) so local dev never fights a stale cache.

## Design tokens (globals.css)

Every font-size, gap/padding/margin and border-radius in `globals.css` uses a token from `:root`. Use them for new UI too, and never hardcode a px value next to them:
- **Type:** `--text-2xs` (10px) … `--text-3xl` (26px). Nothing goes below `--text-2xs`.
- **Spacing:** `--space-0-5` (2px) … `--space-7` (28px), 2px steps, no odd values.
- **Radius:** `--radius-xs` … `--radius-2xl`, plus `--radius-full`. A nested surface is one step smaller than its parent.
- **Per-person colour:** use `--accent` / `--accent-soft`, never `--series-martin` with a `[data-person="laura"]` override. The nearest `[data-person]` ancestor decides the colour, and `.wrap` carries the signed-in person's. `--series-*` is still right where both people show at once (charts, compare columns, dots). The accent vars are declared on `.wrap`/`[data-person]`, not `:root`, because DashboardClient sets custom colours inline on `.wrap`.
- **Contrast:** light-theme `--text-muted`, `--status-good` and `--status-warning` were darkened to pass 4.5:1 as text. Re-check contrast if you change them.
- **Chart & macro colours:** `--over` (over-goal bars, ring and the big "+300"), `--macro-protein/carbs/fat/fiber` (macro dots) and `--bar-dim` (how much the 7-day chart fades other days) are set per scheme in one block near the top of `globals.css`. Use them, not `--status-warning` or the person colours, for those fills: `--status-warning` is a dark *text* colour and turned muddy as a big fill, and the person colours can both be the same pink. Plain opacity on a dark page turns orange brown and pink maroon, which is why night schemes use a higher `--bar-dim`.
- Small icon buttons get a 44px tap area from an invisible `::after` (see "Tap targets" at the end of the file). Add new small buttons to that list.

## PWA / mobile details worth knowing before touching layout or theming

- `app/layout.js` sets `viewport-fit=cover` + an inline script (`THEME_COLOR_SNIPPET`) that resolves the saved colour scheme (incl. "Auto" → device light/dark), always sets `data-theme` on `<html>`, and paints a matching `<meta name="theme-color">` *before* first paint, to avoid a flash of the wrong theme/status-bar color. There is deliberately no static `<meta name="theme-color">` tag in the JSX — the script creates the one and only instance. Don't add a second one.
- Colour schemes: bright **Classic** (`light`, the plain `:root` defaults), **Sand**, **Nordic**, **Blush**; night **Classic** (`dark`), **Midnight**, **Ember** — each a `:root[data-theme="<key>"]` block in `globals.css`, listed (with the `bg` that must equal its `--page`) in `lib/theme.js`, the single source the Colour panel, `DashboardClient` and the layout snippet read. The saved choice (localStorage `nutriscore-theme`) is `{ mode: "day" | "night" | null (Auto), day, night }`; `normalizeTheme()` also upgrades the old `{ mode: "light"|"dark"|"green" }` shape (the old Forest/`green` scheme was retired → night Classic). The layout snippet mirrors `normalizeTheme`/`resolveTheme` by hand in ES5 — change both together. All text/status colours pass 4.5:1 in every scheme; re-check if you add one.
- **App icon (Stride N)** in 5 colours (`lib/appIcons.js`: duo default, bay, sunrise, nordic, gold). The choice is per device, in the `nutriscore_icon` cookie (set by the Colour panel's "App icon" picker). `app/layout.js` reads it server-side to emit the favicon, `apple-touch-icon` and `<link rel="manifest" href="/api/manifest">`; `app/api/manifest/route.js` builds the manifest per request with that scheme's icons (incl. a maskable 512). PNGs in `public/icons/` are generated — edit `scripts/icons/stride.mjs` and re-run `scripts/icons/render-icons.mjs` (needs `VERIFY_DIR`), never hand-edit them. iPhone only reads the icon at Add to Home Screen, so a change needs remove + re-add; Android Chrome updates by itself.
- **Popups lock the page behind them**: `Modal.js` and `SideDrawer.js` call `useScrollLock()` (`app/dashboard/useScrollLock.js`), which pins `body` with `position: fixed` at the current scroll offset and restores it on close (counted, so overlapping popups don't unlock early). `overflow: hidden` alone doesn't stop iPhone scrolling the page when you drag on the backdrop. Any new full-screen popup should use `Modal` or call the hook.
- `window.__nutriscoreApplyThemeColor(key)` (a resolved scheme key) is exposed globally by that inline script so `DashboardClient.js` can re-sync the status bar color whenever the person changes scheme at runtime or their OS dark-mode setting changes while Auto is selected.

"+ Plan" / "+ Add" / tapping your own session opens a sheet with sport chips plus Distance / Time dropdowns (brick: bike km + run km + time; steps in `PLAN_KM`/`PLAN_MIN` in `lib/trainingSports.js`) that write the text via `planText()` ("Run 10 km · 1 h 30"); the text stays editable, and editing a plan reads the dropdowns back from it (`distancesOf`, `timeIn`), slotting in a hand-typed value that isn't a step. The week renders only after mount and formats dates by hand: the server's clock is UTC and Node's `en-GB` date strings differ from the browser's, both of which broke hydration. `TodayPlanStrip.js` refetches on the `nutriscore-plan-changed` window event.

## Deployment history (context, may no longer be the process once this is in real git)

This project was previously edited entirely inside a Cowork cloud sandbox with **no git access** — every deploy was the user manually dragging the whole project folder into GitHub's web upload UI, after Claude exported it as a zip (excluding `node_modules`/`.next`). That process caused two real problems worth knowing about in case artifacts from it remain in the repo:
1. GitHub's web uploader has a soft per-upload file-count limit, so large batches sometimes got split by top-level folder.
2. A stale zip left in the output directory got reused (zip merges into an existing archive by default instead of overwriting), which briefly reintroduced an old nested duplicate `nutriscore-app/` folder into the repo root. **If you see a folder named `nutriscore-app` nested *inside* the app folder (i.e. `nutriscore-app/nutriscore-app/`), that's leftover cruft from this — safe to delete. The top-level `nutriscore-app/` in the `NutriScore-2` repo is the real app; don't delete that one.**

Now that the project is being worked on with real git access, this entire manual-zip workflow should be unnecessary — use normal commits/pushes instead.
